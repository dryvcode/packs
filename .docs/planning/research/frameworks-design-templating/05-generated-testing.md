# Generated testing and verification

Generated tests should become a normal pack design question, but Dryv must distinguish **generator tests** from **tests generated into the user's project**.

## 1. Two different test systems

### Pack conformance tests

These prove the pack itself works against canonical sample IR:

```text
Dryv fixture IR
  → plan/generate pack
  → native formatter/analyzer/compiler/test harness
  → verify generated artifact shape
```

Current packs already use shared fixture IR plus pack-specific native toolchains. This should continue.

### Generated application tests

These are artifacts emitted by the pack into the generated package/project:

```text
Runtime IR meaning
  → pack implementation
  → source + tests
```

They verify the generated application or package, not Dryv itself.

These concerns must never be conflated.

## 2. Framework evidence

### NestJS

Nest scaffolds unit tests and E2E tests. E2E convention uses a `test/` directory and `.e2e-spec` files with a bootstrapped Nest application and HTTP requests.

### Flutter

Flutter distinguishes:

- unit tests for functions/classes;
- widget tests for widgets;
- integration tests for complete apps/large flows.

Current architecture guidance strongly recommends unit tests for services, repositories and ViewModels and widget tests for Views.

### Angular

Unit tests conventionally use `.spec.ts` and are colocated with the source concept. Current CLI projects are configured to run them through `ng test`.

### Spring

Spring Modulith can test one application module in isolation, with direct dependencies, or with all dependencies. This ties test topology to semantic/architectural boundaries.

### Rails

Rails has model/controller/integration/system testing. Current guidance explicitly recommends reserving expensive system/browser tests for critical user paths instead of creating them for every feature.

### ASP.NET Core

Integration tests commonly live in a separate test project referencing the system under test and use a test web host/client.

## 3. What Dryv can generate confidently today

### Contract/adapter tests

Runtime IR already knows enough to verify generated adapters such as:

- HTTP method and effective path;
- path/query/header/cookie/body/form binding;
- success status mapping;
- failure status mapping where declared;
- serialization/deserialization shape;
- validation constraints represented by schemas/properties;
- client request construction;
- generated enum/value representation;
- event payload shape;
- explicit workflow value flow;
- policy attachment/wiring where an implementation pack exposes it.

These tests verify a transformation from canonical meaning to implementation and are ideal generated artifacts.

### Structural/wiring tests

Framework packs can verify their own generated assembly:

- Nest controller is registered in its module;
- FastAPI router is included;
- Spring component/module boundaries compile;
- Flutter view can resolve its injected view model/provider;
- ASP.NET endpoint mapping resolves its service interface.

These are implementation-specific tests generated by packs from semantic/planning facts.

## 4. What Dryv cannot honestly prove from type shape alone

Current smoke packs synthesize values such as:

```text
UUID -> fixed example UUID
email -> test@example.com
number -> 1
date -> fixed date
enum -> first member
```

This can prove request construction and endpoint reachability. It cannot prove business behavior.

For example, the Engine cannot infer that:

```text
CreateOrder(total = 1) should create an order
CancelOrder(id = generated UUID) should succeed
Login(email = test@example.com) should authenticate
```

Those require domain state, meaningful examples or scenarios.

## 5. Proposed verification levels

Pack authors should identify which level a generated test belongs to:

| Level | What it verifies | Semantic requirements |
| --- | --- | --- |
| syntax/static | generated file parses/types/checks | artifact only |
| representation | schema/value maps correctly | Property/Schema meaning |
| adapter contract | transport/client/framework binding matches contract | Operation facets + I/O |
| component/wiring | generated implementation pieces compose | plan/dependency graph |
| scenario | known behavior for known inputs | authored examples/scenarios |
| workflow integration | multi-operation semantic path | Workflow + usable data |
| system/E2E | user-visible critical path | View/navigation/scenario/environment |

This is more useful than calling everything `unit` or `e2e`, because the same semantic proof can be implemented differently per ecosystem.

## 6. Candidate scenario semantics

To generate meaningful behavior tests, research authored examples/scenarios that are implementation-neutral.

Conceptual only:

```yaml
scenarios:
  orders.create-standard:
    invokes:
      operation: { $ref: '#/operations/orders.CreateOrder' }
      input: ...
    expects:
      output: ...
      emits:
        - { $ref: '#/events/orders.OrderCreated' }
```

Another scenario could expect a canonical Failure rather than a transport status.

A Nest pack could turn the scenario into Supertest/Jest/Vitest. A Spring pack could turn it into JUnit. A client SDK pack could use it as a mock contract test. Documentation could render it as an example.

The canonical concept therefore must be behavioral evidence, not a test-framework object.

## 7. HTTP E2E generation

An HTTP backend pack can potentially generate:

```text
valid request → declared success response
invalid constrained field → validation failure
declared Failure → mapped status
authentication required → unauthenticated request denied
idempotency key → repeated request behavior
```

But confidence differs:

- route/binding/status assertions are directly canonical;
- invalid schema-value tests can be mechanically derived where constraints are explicit;
- domain Failure triggering generally requires an authored scenario or controlled fake service;
- auth tests need a pack-defined test authentication strategy;
- persistence tests need deterministic fixture/transaction setup.

Therefore packs should not fabricate business preconditions.

## 8. Frontend tests

View semantics can support generated component/widget tests for:

- a Present Part renders data supplied by a fake Operation result;
- a Collect Part exposes controls for collected semantic paths;
- an Invoke Part calls its bound Operation;
- context-supplied values are not incorrectly exposed as user-editable inputs;
- policy/conditional behavior if canonical View semantics explicitly require it.

Full navigation E2E needs canonical address/navigation meaning. Current View semantics do not provide it, so a pack that invents routes can only test its own invented convention.

## 9. Test data strategy

Potential data sources, from strongest to weakest:

1. authored operation/workflow scenario;
2. authored Schema example;
3. canonical default/value constraints;
4. deterministic generator synthesis;
5. TODO placeholder.

Generated tests should expose which source they used. A synthesized placeholder must never be presented as business truth.

## 10. Test artifact topology

Do not force one universal layout. Framework-native placement should win:

```text
Nest        source *.spec.ts + test/*.e2e-spec.ts
Flutter     test/** + integration_test/**
Angular     colocated *.spec.ts
Rails       test/models, test/controllers, test/integration, test/system
ASP.NET     sibling *.Tests project
Spring      src/test/java/... matching package/module boundaries
```

The pack owns this topology.

## 11. Test selection

Tests should also be selected by semantic reason.

Examples:

```text
HTTP Operation                  → adapter/endpoint test
Schema with constraints         → validation test
Operation declaring Failures    → failure mapping test
View Collect Part               → form/input interaction test
Workflow                        → orchestration test
auth-required Operation         → authorization wiring test
critical authored scenario      → system/E2E test
```

This is another reason to research closed semantic traits in selectors.

## 12. Generated test actions

Pack actions should be able to describe native verification commands such as:

```text
Nest/TS      test, test:e2e, typecheck, build
Flutter      analyze, test, test integration_test
Spring       test
ASP.NET      dotnet test
Rails        bin/rails test
Python       pytest
```

The command names/tools remain pack-level. A neutral action intent such as `test`, `typecheck`, `analyze`, `build` can improve CLI presentation and harness selection without entering Runtime IR.

## Recommendation

Make generated verification a standard pack-design section:

```text
What semantic claims does this pack realize?
Which of those claims can generated tests verify?
Where does the framework expect those tests?
What setup/fakes/fixtures are required?
Which tests are deterministic from IR alone?
Which require authored examples/scenarios?
Which native command proves the generated result?
```

A production pack should explain why it does or does not generate tests.
